# Spine Pair Review — bookvie (Update: Sort direction toggle)

## Overall verdict
This Update is a sound, small contract. D1–D9 and both of Oleg's later calls (↑ natural / ↓ reversed; the toggle joined to the select's right edge as one compound field) are all in the spines, the two component names match, and every new token reference resolves. There are no critical or high findings. The medium findings are places where a story developer or an ATDD writer would still have to guess: whether the reset on a key change is written to storage, what "announced" means for a name change on a focused button, which element paints over the shared edge when either half is focused, a hover that can't be seen and has no token, and the toolbar shifting under the pointer when the label's width changes.

## 2. Token completeness — adequate
Checked: `components.sort-direction-toggle` (DESIGN frontmatter lines 229–236): `{colors.surface-inset}`, `{colors.ink}`, `{colors.input-border}`, `{rounded.md}` (line 162, 9px), `{typography.body-sm}` (line 136), `{colors.ink-secondary}`. All of them resolve. `height: 42px` matches `button-primary`, `page-field` and the Sort select as built (`--button-height` in `SortSelect.module.css`). The 1.5px border matches `text-field`, which is right for a compound field. Prose references `{components.sort-direction-toggle}` and `{components.focus-ring}` resolve. The frontmatter adds only a component, no primitive, so the `e2e/app-shell.spec.ts` primitive comparison and `tokens.css` stay untouched.
### Findings
- **medium** The prose sets "Hover: `surface` fill", but the component has no hover token, and nothing else in DESIGN.md defines hover for a button (`button-secondary` has none). The change is also almost invisible: `surface-inset` vs `surface` is 1.05:1 in light and 1.06:1 in dark. On hover the toggle takes the select's own fill, which removes the "reads as a button, the select as a field" distinction the row relies on. (DESIGN §Components → Sort direction toggle; frontmatter `sort-direction-toggle`). *Fix:* Drop the hover rule so the toggle matches the other secondary buttons: "No hover change, like `button-secondary`; the pointer is the only hover cue." If a hover is wanted, add `background-hover:` to the component and choose a token that differs from the select's `surface`.
- **low** Padding and the gap between the glyph and the text aren't given, so the developer has to guess the toggle's inner layout. (DESIGN frontmatter `sort-direction-toggle`). *Fix:* Add `padding: '0 {spacing.3}'` (the select's left padding) and `gap: '{spacing.1}'`, or state both in the row.
- **low** The contrast table has no rows for the toggle's text pairs. They pass: `ink` on `surface-inset` 13.06 / 13.69, `ink-secondary` on `surface-inset` 5.82 / 8.08 (light / dark). The rule "all load-bearing text pairs meet AA" is stated, but this pairing isn't listed. (DESIGN §Colors → Contrast (computed)). *Fix:* Add `ink` on `surface-inset` (Sort direction toggle text) 13.06 / 13.69 and `ink-secondary` on `surface-inset` (Sort direction glyph) 5.82 / 8.08.

## 3. Component coverage — strong
Checked: the **Sort direction toggle** has a DESIGN Components row (line 661) and an EXPERIENCE Component Patterns row (line 129). The names are identical, and both rows give real rules: anatomy, fill, glyph, focus and forced colors in DESIGN; role, label pairs, name, activation, focus, Tab order, visibility, persistence and reset in EXPERIENCE. The **Sort select** rows in both files were updated: square right corners in DESIGN; natural directions, reversal, ties and reset in EXPERIENCE.
### Findings
- **low** The toggle's accessible name is the order alone ("A–Z", "Newest first"). The "Sort" label names only the select, so a screen reader user who Tabs off the select hears "A–Z, button" with nothing saying it belongs to the sort. Accessibility Floor → Names says toggle groups have group names, but this compound field has none. (EXPERIENCE §Component Patterns → Sort direction toggle; §Accessibility Floor → Names). *Fix:* Optional, and it leaves D4 intact: "The select and the toggle sit in a `role="group"` labelled by the visible 'Sort' label; the button's own name stays its visible text."

## 4. State coverage — adequate
Checked: empty catalog (EXPERIENCE row 129 "not on an empty catalog", which matches State Patterns → No Books "toolbar shows only **New book**"), storage failure (read, empty and junk all mean natural; a failed write still reverses for the visit), key change (reset), focus, hover, forced colors (DESIGN line 566), dark (tokens), and Home's slice (line 289).
### Findings
- **medium** The spines don't say that the reset on a key change is written to storage. "Reversed is remembered" plus "Changing the key resets it" leaves a build that resets only in memory open: with Author Z–A stored and Pages then chosen, a reload would show Pages most first. The plan's P0 "Reset on key change" test asserts that storage holds "not reversed". (EXPERIENCE §Component Patterns → Sort direction toggle; also Sort select row). *Fix:* "Changing the key resets it to natural and remembers that, so a reload after a key change shows the new key's natural order."
- **medium** "Nothing is announced besides the new name" reads as a promise that the name change is spoken. A name change on a focused `button` isn't reliably re-read by screen readers in Chrome, and an ATDD writer can't test it. The rest of the spine routes outcomes through the polite `status` region. (EXPERIENCE §Component Patterns → Sort direction toggle; §Accessibility Floor → Live regions). *Fix:* Make it testable: "The `status` region stays silent; the button's new name is the only feedback." Or, if Oleg wants it spoken, add the toggle to Live regions with "Sorted Z–A." Either way, say which.
- **medium** The two focus treatments meet at the shared edge and the spine doesn't say which one paints on top. The toggle's `{components.focus-ring}` is a 2px outline at a 2px offset, so its left side lands over the select. The select's Text field focus (an `accent` border plus a 4px `focus-halo`) spreads over the toggle. "Drawn above the shared edge" can be read as either position or stacking order. It also doesn't say who owns the shared edge. (DESIGN §Components → Sort direction toggle, Text field, Focus ring). *Fix:* "The shared edge is the select's right border: it turns `accent` when the select has focus. Whichever half has focus is raised above the other (`position: relative; z-index: 1`), so its ring or halo is never clipped by the other half."
- **medium** "Its width follows its text, so it may change when the key or direction changes." Pressing the toggle changes "Fewest first" to "Most first" and "Newest first" to "Oldest first", so the button changes width under the pointer and the view toggle and **New book** to its right shift on every press, which is a layout shift caused by the user's own click. (DESIGN §Components → Sort direction toggle). *Fix:* "Its minimum width is the wider label of the current key's pair, so pressing it never moves the toolbar; only a key change may change its width."
- **low** "Ties go by title A–Z, then the older Book first": "older" could be read as the edition Year rather than Date added. (EXPERIENCE §Component Patterns → Sort select). *Fix:* "…then the Book added earlier first."
- **low** "Reversed is remembered on this computer, apart from the key": "apart from" can be read as "except for". (EXPERIENCE §Component Patterns → Sort direction toggle). *Fix:* "…remembered on this computer, stored separately from the key."
- **low** A stored junk key reads as Author, but a valid stored "reversed" would then reverse Author, a key the reversal was never set for (against D5's reasoning). This is rare. (EXPERIENCE §Component Patterns → Sort direction toggle). *Fix:* "If the stored key can't be read or isn't one of the four, the direction is natural too."

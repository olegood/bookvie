Component coverage

strong

Checked: every component the change names. The Checkbox has a DESIGN Components row and a frontmatter entry. Its behavior is native and specified where it's used: EXPERIENCE → Card note panel → Add another says what it controls, its default, that it is remembered, and that it shows in add mode only. aria-keyshortcuts="Meta+Enter Control+Enter" sits on Save note, but the keys work only while focus is in Note. The Pile's shortcuts work anywhere in the pile. A screen reader user on Save note or in Page hears a shortcut that does nothing there. (Cmd+Enter in Page isn't specified either.)

EXPERIENCE §Card note panel → Keyboard save
Fix: Either accept this and say so ("the shortcut applies in Note"), or put the attribute on the Note field. The plan's D1 chose the button, so changing it is Oleg's call. (applied in this Update)

State coverage

adequate

Checked: empty (opening focus on Note, prefilled Page), validation error, couldn't save (State Patterns row lists Card note; "Failures never close it" matches D8), after save with Add another off (closes, as before) and on (stays open, Note empties, Page kept, errors cleared, focus on Note, announced again), edit mode (no checkbox, Cmd+Enter works), storage unreadable (off), running count (starts empty on each opening, not a live region). The live-region rule (empty both regions, set text after about 100 ms) makes the repeated "Card note saved." announce again, which matches the plan.

medium

The saving state isn't defined, and the new text contradicts Foundation. Keyboard save says Cmd+Enter has "the same … busy state" as Save note. But Foundation says "The only busy states are Export and Restore", and no section describes Save note while a save is out. The code makes Save note aria-disabled during the save; the spine never says so.

EXPERIENCE §Card note panel → Keyboard save; §Foundation → Local-first; §Accessibility Floor → Focus
Fix: State the panel's in-flight behavior in one line, for example "While a save is out, Save note is aria-disabled and further presses, Cmd+Enter included, are ignored; its label doesn't change". Then narrow Foundation's sentence to "the only busy labels are Export and Restore". (applied in this Update)
medium

Cancel or Esc while a save is out isn't specified. Rapid entry ("Cmd+Enter, Esc") makes this likely. The plan records that Esc is ignored in flight today. Without that in the spine, a builder could close the panel mid-save, and the save would then land, or fail, with no panel left to show the couldn't-save line.

EXPERIENCE §Card note panel → Cancel after saves; §Interaction Primitives → Esc
Fix: Add "Cancel and Esc are ignored while a save is out; once it lands, the panel follows Add another as usual." (applied in this Update)
low

Storage edges are only partly covered. "Storage that can't be read means off" covers a read that throws. D3 also says empty or junk reads as off, and nothing says what happens when the write fails while toggling (presumably the checkbox still toggles for this opening, silently).

EXPERIENCE §Card note panel → Add another
Fix: "A missing, unreadable or unrecognized value means off; if it can't be stored, the choice still applies until the page reloads." (applied in this Update)
low

"Save note saves and closes" is still stated without a condition, two bullets above the exception for Add another being on. A reader skimming top-down meets the absolute rule first.

EXPERIENCE §Card note panel, the Save note bullet; Focus after close row "Card note panel | Save or Cancel"
Fix: "Save note saves and closes (unless Add another is on, below)", and in Focus after close: "Save (Add another off, or edit mode) or Cancel". (applied in this Update)
low

Edit mode with the remembered choice on: it's clear only by inference that an edit save closes even when the stored value is on.

EXPERIENCE §Card note panel → Add another; Edit mode
Fix: Add "In edit mode the remembered choice is ignored and a save closes" to the Edit mode bullet. (applied in this Update)

Inheritance discipline

The dark twin of accent comes from the theme's token swap (tokens.css redefines --accent under the dark selectors), so accent-color must reference the token variable, not a literal. Someone following the sentence literally could hard-code #557059 and expect color-scheme to swap it.

DESIGN §Components → Checkbox
Fix: "…accent-color: var(--accent), so the dark theme's token swap gives the accent dark twin, and color-scheme: dark gives the dark box." (applied in this Update)

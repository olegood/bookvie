## Intent

**Problem:** An agent can read the library and record reading (12.2, 12.3), but it can't add a Book or correct one. Cataloging from Claude Code needs the New book panel's checks, so it can't create duplicates or half-filled Books.

**Approach:** Register `add_book` and `edit_book` write tools after `unmark_side_read`, each with the story's description verbatim. They parse with the route's `parse_add_book_intent` / `parse_edit_book_intent` and call the route's handlers, so they store, answer and refuse as `POST /api/intents/add-book` / `edit-book` do. `edit_book` is a whole edit: its schema requires every form key plus `bookId`, and a call missing any of them is refused with `invalid_fields` before the handler runs. So an agent can send a Book's current values back, `get_book`'s view (shared with `GET /api/views/book`) gains `editForm`: the 13 form fields as the Edit book panel prefills them (`toPanelFields`), every one a string.

## Boundaries & Constraints

**Always:** The add-book tool advertises `input_schema(AddBookIntent)` unchanged. The edit-book tool advertises `input_schema(EditBookIntent)` with `required` = every form key plus `bookId`; nothing else in its schema differs. The route's parser is the only validator of a call that has every required key (a wrong type, `null` or an unknown key is the route's `intent` refusal). Answers are the routes': `{ok: true, ids: {bookId}}` and `{ok: true}`, built by shared `intents.answers` functions the routes use too. `agent/` imports only `intents` and `views`.

**Never:** No `coverUrl` (Story 12.5). No change to the intent routes' behavior. The only OpenAPI change is `editForm` on the book detail view (`schema.d.ts` regenerated by `api:gen`, never by hand); the panel keeps its own `toPanelFields`. No merge with the stored Book in `edit_book`. No `delete_book` tool. No edit to existing leaves' assertions beyond the cumulative tool lists.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Add | valid form keys | Book stored, `{ok, ids: {bookId}}` | — |
| Edit, whole | every form key + `bookId` | Book replaced, `{ok: true}`; an unchanged edit still commits | — |
| Edit, partial | `{bookId, title}` | nothing stored | `invalid_fields`, one field per missing key named by its key, message "Field required", in schema order |
| Invalid / duplicate / not found / pages floor / fault | as the route | as the route | the route's AD-9 error |
| Round trip | `get_book`'s `editForm` + `bookId`, for every seeded Book (finished, paused, unread, with a cover, with a user color, with a curated color only) | `{ok: true}`, `library.json` byte-identical | — |
| editForm shape | a Book with authors, tags, year, a finish date, a curated color and no user color | strings: authors "; "-joined, tags ", "-joined, numbers as decimal strings, `finishedOn` the latest finish date or "", `spineColor` `spineColorUser` or "" | — |

## Design Notes

The required-key check lives on the tool, not the model: `EditBookIntent` stays the route's model, so the route keeps treating an omitted key as empty. `required` holds aliases; the check is `[k for k in schema["required"] if k not in arguments]`, so `bookId` (already required by the model) is named too when missing.

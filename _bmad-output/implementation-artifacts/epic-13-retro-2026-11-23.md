### Diff-scope review (story boundaries)

The restore path holds up:

- **The token** (`restore_gate.py`): HMAC with a per-app key and a process nonce, single use, spent even when expired.
- **The apply** (`restore_file.apply_confirmed_restore`): one hold of the lock covers both hash re-checks, a single read, staging, the safety copy and the apply.
- **The path checks** (`backup_file._locate_backup`, `_read_once` with `O_NOFOLLOW`).

The findings are at the seams between bookvie, bookvie-dropbox and the two skills.

- **E13-B1 (medium, fix now). The Backup page and the skill can say "Nothing in Dropbox was deleted" when today's copy was already replaced.**
  - On a mismatch found after the finish, `upload_backup` answers `upload_incomplete`, and its message says it "has already replaced any earlier copy" (`bookvie_dropbox/upload.py:271`).
  - The skill drops the message and prints a fixed line: "Failed: the last upload didn't finish. Nothing in Dropbox was deleted; run /bookvie-backup again." (`.claude/skills/bookvie-backup/SKILL.md`, step 6). The page shows the same reason (`frontend/src/lib/dropboxBackupLine.ts:14`), and so does the guide (`docs/dropbox-backup.md:94`).
  - The known entry `deferred-work.md:1549` (Medium) records the replacement, but not that the user is told the opposite.
- **E13-B2 (medium-low, fix now with B1). If the prune fails after a verified upload, the run is recorded as `failed/other`.**
  - `upload.py:322-331` raises `other` after the upload is verified. The skill records `failed` with that cause (`SKILL.md` step 5), so `lastUpload` stays at the previous day.
  - The page then reads "failed … the last run stopped with an error. Last upload on <previous day>", although Dropbox holds today's checked copy. The next run uploads again, because the stored hash is stale.
  - The test pins this behavior (`test_backup_skill.py:491`).
- **E13-B3 (low, accept).** Uploading an older daily prunes a newer one, because the prune keeps the two newest *other* dailies plus the one just written (`upload.py:313-318`). A test pins it on purpose (`test_dropbox_upload_edges.py:180`). The skill always uploads today's file, so only a hand-made agent call can trigger it.
- **E13-B4 (low, defer).** `bookvie_dropbox` hard-codes `~/bookvie-backups`, while bookvie's backups folder follows `--data-dir` (`upload.py:98-104`, `download.py:157`, `backup_file.py:106-123`). On a custom data folder, every backup run fails as `other`, and a Dropbox pick lands outside what `preview_restore` allows. Oleg uses the defaults.
- **E13-B5 (low, defer). A restore followed by a backup the same day overwrites today's Dropbox copy with the restored, older library.** The safety copy, which holds the library from before the restore, is never uploaded (AD-22). It survives on this computer only.
- **E13-B6 (low, defer). A skipped run still rewrites today's local daily.** `export_backup({forUpload: true})` writes a byte-different zip (`backup_file.py:156-196`). Its content hash then differs from Dropbox's copy of the same day, so `/bookvie-restore` shows two rows for one day instead of one.
- **E13-B7 (low, defer).** `download_backup` replaces an earlier `from-dropbox/<name>` with different content without saying so (`download.py:205`).
- **E13-B8 (low, defer).** `list_local_backups` hashes every listed file in full on each call, and nothing prunes the local folder (`backup_file.py:436-451`). One AC-6 download was 75 MB.
- **E13-B9 (low, watch).** All six AC-6 runs were on `--dev` (`target: "bookvie-dev"`). The production path, `target: "bookvie"` into `~/bookvie-backups/from-dropbox`, has had no end-to-end run. Oleg's first real restore will be that run.
- **E13-V1 (medium, fix now). The port-8790 sign-in tests are still flaky under `npm run check`.**
  - This is `deferred-work.md:1567`, open since Story 13.3. It failed 4 of 7 checks in the 13.3 build and 1 of 2 in this retro.

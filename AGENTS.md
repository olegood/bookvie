# AGENTS.md

Instructions for AI agents working in this repository. The [README](README.md) explains what bookvie is and how to run it.

## Formatters

Two formatters are enforced. `npm run check` fails on unformatted code, and so does CI.

| Code | Formatter | Config | Enforced by |
|---|---|---|---|
| Python under `backend/` | ruff 0.16 (`ruff format`, then `ruff check` with rules E, F, I, UP, B) | `[tool.ruff]` in `backend/pyproject.toml` | `npm run check:py` |
| TypeScript, TSX and CSS under `frontend/`, and the `.mjs` scripts | Prettier 3.6 (120 columns, no semicolons, single quotes) | `.prettierrc.json` at the repo root; exclusions in `frontend/.prettierignore` | `npm run check:api` |

**Commands.** Run these from the repo root:

- `npm run format` formats everything: Prettier, then `ruff check --fix` and `ruff format`.
- `npm --prefix frontend run format` formats only the frontend, and `npm --prefix frontend run format:check` checks it.
- `cd backend && uv run ruff format .` formats only the backend, and `cd backend && uv run ruff check .` lints it.

**Rules:**

- Use only the project's pinned tools: `uv run ruff` from `backend/` and the `prettier` installed in `frontend/node_modules`. Never run a global `ruff`, `uvx ruff`, or `npx prettier` from outside `frontend/`. Those can pick up another version or a user-level config, and they reformat code differently. A user-level ruff config is the source of rule names like S110 or PLW1510 that this project doesn't use.
- Format only the files you changed (`npx prettier --write <file>` inside `frontend/`, `uv run ruff format <file>` inside `backend/`), or run `npm run format`. Don't run a formatter with options other than the config's.
- Never format these two files, which both formatters already skip:
  - `frontend/src/api/generated/schema.d.ts` is generated by `npm --prefix frontend run api:gen`, and `check:api` compares it byte for byte.
  - `frontend/src/styles/tokens.css` copies DESIGN.md's tokens character for character, and `e2e/app-shell.spec.ts` compares them.
- Markdown, JSON and YAML have no formatter. Match the surrounding style by hand.

**Lint.** oxlint (`frontend/.oxlintrc.json`) and `tsc -b` run in `check:api`. ruff's lint runs in `check:py`.

**Blame.** The one-time reformat is listed in `.git-blame-ignore-revs`. To have `git blame` skip it, run `git config blame.ignoreRevsFile .git-blame-ignore-revs`.

## Architecture spine

The spine is `_bmad-output/planning-artifacts/architecture/architecture-bookvie-2026-10-29/ARCHITECTURE-SPINE.md`. It is reconciled once per epic, not per story (Epic 3 retro item 24, which supersedes Epic 2 item 16):

- **During a story,** the spine-check review layer still runs. A finding where the code is right and the spine is out of date is spine drift: defer it to `_bmad-output/implementation-artifacts/deferred-work.md` with the words "spine drift" and the AD it names, and close the story. The marker is what the retro and the next-epic gate look for, since "spine" alone also means a Book's spine. They match it in any letter case, because entries usually write "Spine drift" (Epic 4 retro item 39). Drift doesn't block a story. Don't edit the spine inside a story.
- **A finding where the code breaks a decision it should follow** is not drift. Fix it in the story like any other review finding.
- **The retrospective** always proposes an action item to reconcile the spine with the epic, listing that epic's unresolved "spine drift" entries in `deferred-work.md`.
- **Before the next epic's first story,** that reconciliation lands: one pass edits the spine and adds a `resolved:` line to each drift entry it closes. `bmad-build` and `bmad-build-auto` stop at the first story of an epic while the previous epic has unresolved "spine drift" entries, unless you tell them to proceed.

## Story pipeline

Every story gets these four steps, in this order (Epic 4 retro item 40):

1. `bmad-testarch-atdd`: the red-phase acceptance tests.
2. `bmad-build-auto`: the build. It ends with the story in review, not `done`.
3. `bmad-code-review`: the only step that marks a story `done`. After any patch, however small, it re-runs the full `npm run check` before it marks the story `done`; a review with no patch doesn't need to. Its commit type follows the files the commit changes, not the step: `docs:` only when every file is Markdown or `sprint-status.yaml`, otherwise `fix:`, `test:` or `chore:` (Epic 8 retro item 63).
4. `bmad-testarch-automate`: runs only after the story is `done`.

Don't skip or merge a step. The review inside `bmad-build-auto` doesn't replace step 3.

Step 3 runs in a new session, never in the session that ran step 2, so the review is independent of the build (Epic 5 retro item 47). A compacted or resumed build session is not new: it still carries the build's summary. Re-run any probe, check or test result the review relies on. Don't cite the build's results, its Auto Run Result, or a probe from earlier in a conversation as evidence. Step 4 likewise re-runs what it relies on.

Keep work outside the story out of the working tree while any of its steps runs (Epic 6 retro item 56). A story's ATDD, build, review and automate all run in the shared checkout. Other work, such as a skill change or a docs fix, goes in its own git worktree (`git worktree add`). Never `git switch` or commit in the shared tree while a story step is running. During Story 6.3, a skill session did both: a commit landed in the middle of the story, and the review ran its checks on another branch with uncommitted skill edits present.

Step 2 is `bmad-build-auto`, not the interactive `bmad-build`. bmad-build stops at a story and asks; it continues only when you explicitly say to continue with bmad-build, and records that in the spec. This also applies to a standalone spec with a `- **Pipeline:**` line that names `bmad-code-review` after `bmad-build-auto`.

## Epic boundaries

When a story closes its epic (every other story of the epic is `done` in `sprint-status.yaml`), don't start the next epic's first story, even though the retrospective's status reads `optional`. First come test automation for that story (`bmad-testarch-automate`), the epic's retrospective (`bmad-retrospective`), and the retro's before-next-epic items: the trace and gate and the spine reconciliation. `bmad-code-review` offers the first two instead of "Start the next story" at an epic's last story (Epic 3 retro item 30).

## Supported browser

bookvie supports desktop Chrome only, and the e2e suite runs Chromium only (`projects` in `frontend/playwright.config.ts`). Oleg uses Chrome. That was decided in the Epic 4 retro (`deferred-work.md`, "Deferred from: implementation of spec-4-3-pause-my-main-book") and confirmed in the Epic 7 retro (item 59), after both of Story 7.2's reviews raised Safari mouse-focus behavior that no one could run (Epic 7 retro PL-2).

- **When building or reviewing,** treat behavior that only Safari or Firefox would show as out of scope. This includes a macOS Safari click that doesn't focus the button it presses. Don't add a workaround or a test for it. In a review, reject such a finding with that reason and cite this section, unless Oleg reopens the decision.
- **Behavior that Chromium shows too** is in scope as usual, even when someone first noticed it while thinking about another browser.
- **Kept from before this rule:** Story 7.2's focus-on-click in `FilterChips.tsx` (commit `0383cbc`) and its two tests that model a focusless click, `catalog-filter.spec.ts:471` and `:582`. They stay, because focusing the pressed control is also correct in Chromium. They aren't a precedent for more.
